# 자체 서버 없는 무료 출시 제안 검토

작성일: 2026-10-09 · 대상: 말이음 / SpeechBridge

## 1. 종합 의견

**Dots의 제안은 조건부로 타당하다.** 문장 연습, 녹음·비교 재생, OCR, 로컬 기록, 단순 발성 놀이를 중심으로 구성하면 자체 백엔드와 유료 분석 API 없이 사용자에게 무료로 제공할 수 있다. 현재 저장소에도 이 방향의 구현이 상당 부분 존재한다.

다만 **자체 서버 없음, 완전 오프라인, 사용자 이용료 무료, 개발·출시 총비용 0원은 서로 다른 조건**이다. 앱스토어 등록비, 기기별 음성 인식 의존성, 설치 용량, 콘텐츠 관리와 검증 비용을 제외한 채 “무료 출시 가능”이라고 단정하면 부정확하다.

권고: **첫 버전은 ‘기기에서 문장을 연습하고 자신의 녹음을 비교하는 무료 연습 도구’로 출시한다.** 서버 분석과 자동 발음 채점은 제외하고, 음성 인식이 실패해도 핵심 연습을 끝낼 수 있게 한다. 현재 코드가 그대로 출시 가능한 상태라는 판정은 아니다.

검토 범위는 사용자가 제공한 Dots 답변, 저장소의 관련 코드·문서, 공식 플랫폼 문서다. 실기기 실행·스토어 심사·임상 검증은 이번 검토에서 수행하지 않았다. 기존 Graphify 그래프 조회에서는 해당 기능의 일치 노드가 나오지 않아 아래 판단은 실제 소스 확인에 근거한다.

## 2. Dots 답변의 항목별 판정

| 제안 | 판정 | 출시 조건 |
|---|---|---|
| 자체 서버 없이 출시 | 가능 | 분석 업로드·로그인·원격 운영이 핵심 경로에 없어야 함 |
| 무료 출시 | 표현 수정 | 사용자 이용료와 자체 서버비는 0원 설계 가능. 스토어 등록비와 개발·운영 노동은 별도 |
| 문장 연습 | 적극 채택 | 내장 문장·직접 입력·수동 완료를 기본으로 제공 |
| 녹음·비교 재생 | 첫 버전의 핵심 | 두 녹음의 번갈아 듣기와 개별 삭제. 자동 정확도 평가와 구분 |
| OCR | 채택 | 한국어·영어 기기 내 인식, 사용자가 수정·확정 후 저장 |
| 로컬 기록 | 채택 | 재실행 후 유지, 저장 실패·용량 부족 처리, 삭제·내보내기 정책 필요 |
| 호흡·목소리 게임 | 범위를 좁혀 채택 | 로컬 음량·발성 감지 기반 놀이 우선. 음성 인식 기반 게임은 별도 조건부 기능 |

## 3. 현재 프로젝트와의 대조

### 이미 활용할 수 있는 기반

- **문장과 두 녹음:** `SentenceRepository`는 앱 지원 디렉터리의 SQLite DB와 녹음 파일을 사용한다. 녹음 슬롯 0·1 구조가 있으며, 문장 화면에는 두 녹음을 비교하는 흐름이 있다. 이 핵심 기능에 원격 DB는 필요하지 않다.
- **OCR:** Flutter `SentenceOcr`가 네이티브 채널을 호출한다. Android는 한국어·라틴 문자 ML Kit, iOS는 Apple Vision을 사용한다. Android Gradle에는 모델을 앱에 포함하는 `com.google.mlkit` 의존성이 등록되어 있다. iOS 코드는 지원 언어를 확인하고 미지원 오류를 반환한다.
- **로컬 발성 분석:** `lib/services/audio_analysis/`에 입력 스트림, 신호 분석, WAV 파일과 기록 관련 구현이 있다. 로컬 신호에 반응하는 놀이와 서버에서 문장을 해석하는 분석은 분리할 수 있다.
- **내장 훈련 정책:** 리소스 관리 문서는 원격 카탈로그 없이 내장 정책으로 동작하는 경로를 설명한다. 서버가 없다고 모든 훈련이 막히는 구조는 아니다.

위 항목은 코드 구조의 확인이다. 모바일 배포판에서의 정확도·안정성·접근성 확인을 대체하지 않는다.

### 출시 전에 정리할 실제 의존성

**① 서버 분석은 단순히 서버를 끄는 것으로 정리되지 않는다.**

`SentenceAnalysisClient`에는 `SENTENCE_ANALYSIS_URL`이 있고 기본값은 개발용 `http://127.0.0.1:8001`이다. 릴리스 검증에서는 이 HTTP 주소를 허용하지 않는다. 따라서 설정을 생략한 채 분석 버튼을 남기면 사용할 수 없는 기능이 된다. 서버 없는 배포에서는 분석 버튼·상태 조회·재시도 경로를 함께 비활성화하거나 제외해야 한다. 기존 사용자 데이터에 원격 작업이 있으면 삭제 흐름이 서버 정리를 요구하는 부분도 별도 점검한다.

**② OS 음성 인식은 완전 오프라인으로 보장되어 있지 않다.**

공통 `SttService`의 `SpeechListenOptions`와 iOS 네이티브 요청에서 온디바이스 전용 설정을 확인하지 못했다. 게임 문서도 단어 게임과 한 음절 달리기가 OS 음성 인식에 의존한다고 명시한다. 자체 분석 서버가 없어도 OS 제공자의 서버가 사용될 수 있다. Apple은 지원 여부 확인이 필요하며 Android도 원격 인식 가능성을 안내한다. [Apple 음성 인식](https://developer.apple.com/documentation/speech/sfspeechrecognizer/supportsondevicerecognition), [Android SpeechRecognizer](https://developer.android.com/reference/android/speech/SpeechRecognizer)

첫 버전에서는 발성 감지 게임을 기본으로 하고, 음절·단어 인식 게임은 네트워크 의존성과 실패 안내를 명시하거나 후속 버전으로 미룬다. 버튼 조작은 접근성 대안이지 음성 연습 성공과 같은 기록으로 처리할 수 없다.

**③ TTS도 기기별 확인이 필요하다.**

현재 `TtsService`는 OS 음성 합성 기능을 사용한다. 로컬 음성 설치 여부와 엔진에 따라 결과가 달라질 수 있으므로 한국어·영어 오프라인 재생을 확인한다. 실패해도 문장을 읽고 녹음하는 과정은 계속 가능해야 한다. 필수 예시는 배포 권리가 확보된 짧은 음원으로 내장하는 대안이 있다.

**④ 대형 AI 모델은 첫 버전에서 제외하는 편이 합리적이다.**

`pubspec.yaml`에 `assets/gemma-2b-it-gpu-int4.bin`이 앱 자산으로 등록되어 있고 실제 파일은 약 1.3GB다. `flutter_gemma`와 로컬 AI 서비스도 존재한다. API 사용료가 없더라도 다운로드·설치 용량과 기기 성능 부담은 크다. 권장 기능에 자유 생성 AI가 필수적이지 않으므로 첫 배포 구성에서 모델과 호출 경로를 제외하는 방안을 권고한다. 실제 AAB/IPA 크기는 별도 빌드로 측정해야 하며, 이 파일 크기를 배포 파일 크기로 단정할 수 없다.

**⑤ 원격 콘텐츠 운영은 선택 사항이다.**

`RESOURCE_CATALOG_URL`을 이용하는 원격 카탈로그·팩 다운로드는 자체 연산 서버와 다른 의존성이다. 첫 버전은 필요한 문장·안내·영상만 내장하고 앱 업데이트로 수정할 수 있다. 추후 정적 호스팅으로 서명 카탈로그를 제공할 수 있지만 무료 제공량·트래픽 한도는 별도 검토 대상이다. 오프라인 앱에는 즉시 원격 차단이 보장되지 않는다.

## 4. 무료의 범위와 출시 경로

| 비용·의존성 | 권장 첫 버전 |
|---|---|
| 사용자 구매·구독료 | 0원으로 제공 가능 |
| 자체 백엔드·음성 분석 API | 사용하지 않으면 해당 운영비 0원 |
| Google Play 등록 | 개발자 계정 등록비 US$25, 1회. 기존 계정 여부에 따라 추가 부담이 다름 |
| Apple App Store 등록 | 일반 Apple Developer Program US$99/년. 현지 통화·면제 자격 별도 |
| 콘텐츠·음원·영상 제작 | 직접 제작·권리 확보가 필요하며 반드시 무료라고 볼 수 없음 |
| 개발·QA·지원 | 인력·테스트 기기·유지보수 비용 또는 시간이 남음 |
| 정적 안내 페이지 | 무료 호스팅 활용 가능성이 있으나 서비스 조건을 확인해야 함 |

등록비 근거: [Google Play 계정 안내](https://support.google.com/googleplay/android-developer/answer/6112435), [Apple 등록 안내](https://developer.apple.com/help/account/membership/program-enrollment/).

예산 우선이라면 Android부터 검증하는 방안이 합리적이다. 다만 대상 사용자가 iPhone·iPad 중심이라면 사용자 기기를 우선한다. 웹/PWA로 바꾸는 것은 현재 네이티브 OCR·파일 저장·음성 처리 구현을 그대로 배포하는 대안이 아니므로 별도 개발 범위로 본다.

Google Play의 2023-11-13 이후 생성 개인 계정에는 최소 12명, 연속 14일의 비공개 테스트와 프로덕션 접근 신청 요건이 있다. 이는 모든 계정에 일괄 적용되는 조건은 아니다. 의료 앱에 해당하는지와 조직 계정 필요 여부도 제품 기능·표현에 맞춰 확인해야 한다. [테스트 요건](https://support.google.com/googleplay/android-developer/answer/14151465), [계정 유형 안내](https://support.google.com/googleplay/android-developer/answer/13634885)

## 5. 권장 MVP

핵심 흐름은 **문장 고르기 → 읽고 녹음 → 다시 녹음 → 두 녹음 듣기 → 내 느낌과 연습 기록 남기기**다.

| 우선순위 | 포함할 범위 | 완료 기준 |
|---|---|---|
| 필수 | 내장 문장·직접 입력 | 인식 기능 없이도 연습 완료 |
| 필수 | 두 녹음 저장·재생·삭제 | 앱 재시작 후 재생 가능, 저장 실패 시 성공 표시 금지 |
| 필수 | 로컬 기록 | 날짜·문장·연습 횟수·자가 느낌 확인 |
| 필수 | 데이터 관리 | 삭제 범위·재설치 시 손실 가능성 안내, 내보내기 정책 결정 |
| 권장 | 사진 OCR | 잘못 인식된 문장 수정 후 확정, 실패 시 직접 입력 |
| 권장 | 간단한 발성 놀이 1종 | 로컬 감지, 쉬기·종료 접근 가능, 인식 실패로 연습 차단 금지 |
| 조건부 | TTS | 지원 기기 확인, 실패 시 읽기·녹음은 유지 |
| 후속 | 단어·음절 음성 인식 게임 | 네트워크·기기 지원·오인식 대응 확인 후 제공 |
| 후속 | 서버 분석·AI 개인 코칭·계정·동기화 | 비용·보안·품질 검증과 운영 책임을 정한 후 도입 |

OCR은 첫 버전에 넣을 가치가 있지만 녹음·재생 안정성보다 우선하지 않는다. 게임 여러 개보다 하나의 반복 사용 흐름을 안정적으로 완성하는 편이 출시 목적에 맞다.

## 6. 데이터와 제품 표현

로컬 저장은 자동 백업이나 기기 변경 복원을 뜻하지 않는다. 앱 삭제·기기 고장에 대비한 안내와 사용자 주도 내보내기를 검토한다. 녹음 파일과 DB의 연결이 깨지지 않도록 저장 실패·중단 복구를 확인하고, 삭제는 파일과 메타데이터를 함께 처리한다.

“음성이 절대 외부로 나가지 않는다”는 표현은 현재 OS 음성 인식 경로를 둔 상태에서 사용하면 안 된다. 서버 분석을 제외하더라도 OS 인식, 기기 백업, 공유 기능과 SDK 동작을 확인한 후 개인정보 설명을 작성해야 한다.

제품은 연습 보조 역할을 명확히 한다. 파형·발성 시간·인식된 글의 일치를 발음 정확도, 치료 효과 또는 임상 평가 점수로 바꾸어 표시하지 않는다. 마이크 신호만으로 폐활량이나 호흡 기능을 측정한다고 표현하지 않는다. 게임의 성공 조건은 큰 소리·긴 숨 경쟁 대신 편안한 참여와 쉬기 중심으로 설계한다.

Google Play의 건강 관련 기능 정책에는 건강 앱 신고와 개인정보처리방침 등 요건이 있다. 이 프로젝트의 재활 관련 표현을 고려하면 서버 유무와 별개로 출시 항목에 포함해야 한다. ‘연습용’이라는 문구만으로 의료기기 해당 여부가 결정되는 것은 아니며, 출시 국가와 실제 기능·표현에 대한 검토가 필요하다. [Google Play 건강 콘텐츠 정책](https://support.google.com/googleplay/android-developer/answer/16679511)

## 7. 출시 전 통과 조건

아래는 앞으로 수행할 확인 항목이며 이번 검토에서 통과했다고 판단한 항목이 아니다.

1. **배포 범위:** 분석 업로드·로그인·원격 대기 화면을 핵심 경로에서 제거하고 개발 서버 주소로 요청하지 않는다.
2. **오프라인:** 배포판 첫 실행과 재실행을 비행기 모드에서 검사한다. 문장 선택·녹음·비교·기록·삭제가 동작한다. 최초 모델·음성 다운로드가 필요한 경우 이를 구분한다.
3. **OCR:** Android/iOS 한국어·영어, 회전·흐린 이미지·빈 결과·권한 거부를 확인한다. ML Kit 모델 번들 방식과 Apple OS별 언어 지원을 확인한다.
4. **음성:** 전화·백그라운드 전환·이어폰 전환·권한 거부·다른 앱의 마이크 사용 후 정상 복구한다. TTS 소리를 사용자 발성으로 기록하지 않는다.
5. **기록:** 저장 공간 부족·강제 종료·앱 업데이트에서 손상 여부를 확인한다. 삭제·공유·OS 백업 범위와 안내가 일치한다.
6. **설치 용량:** Gemma 포함 여부와 불필요한 영상·모델을 정리한 뒤 AAB/IPA 및 실제 설치 크기를 측정한다.
7. **사용성:** 큰 글자·작은 화면·스크린리더·한 손 조작을 확인하고, 음성 인식 실패가 사용자의 실패 점수로 축적되지 않게 한다.
8. **스토어:** 계정 유형, 테스트 요건, 권한 설명, 개인정보처리방침, 데이터 신고, 건강 관련 표현과 콘텐츠 배포 권리를 확인한다.

OCR 구현 참고: [Android ML Kit 모델 번들·언어 안내](https://developers.google.com/ml-kit/vision/text-recognition/v2/android). 현재 iOS 구현은 ML Kit가 아닌 Apple Vision이므로 Android 지원 결과로 iOS 지원을 대신 판정하지 않는다.

## 8. 실행 순서와 최종 권고

**1단계 — 범위 고정:** 문장·녹음 비교·기록을 필수로, OCR·발성 놀이 1종을 추가 범위로 정한다. 사용자 무료 제공과 백엔드 미운영을 제품 원칙으로 명시한다.

**2단계 — 배포 구성 정리:** 서버 분석 노출, OS 음성 인식 의존성, Gemma 모델 포함, 내장 콘텐츠를 정리한다. 이 검토에서는 실제 코드 변경을 수행하지 않았다.

**3단계 — 실제 기기 검증:** 오프라인과 실패 상황을 검증하고 대상 사용자의 연습 완료 여부를 확인한다. 결과에 따라 추가 기능을 줄여도 핵심 흐름은 유지한다.

**4단계 — 스토어 준비:** 비용과 계정 요건을 확인하고 개인정보·권한·건강 관련 설명을 갖춘 뒤 테스트 배포한다.

Dots 답변은 다음처럼 고치면 정확하다.

> 자체 백엔드와 유료 분석 API 없이, 사용자에게 무료로 제공하는 첫 버전은 가능합니다. 문장 연습·녹음 비교·기기 내 OCR·로컬 기록·단순 발성 놀이를 중심으로 구성하세요. 다만 앱스토어 등록비와 검증·유지보수 부담은 남으며, OS 음성 인식과 TTS의 오프라인 지원은 기기별로 확인해야 합니다. 현재 프로젝트에서는 서버 분석 경로와 대형 AI 모델을 배포 범위에서 정리한 후 출시를 검토하는 것이 적절합니다.
